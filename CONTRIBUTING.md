# Contributing to CABID

Thanks for looking. CABID is an alpha research prototype, so the highest-value
contributions are usually **rule packs, fixtures, and documentation corrections**
rather than new scoring machinery.

## Ground rules

- **No runtime dependencies.** The core must stay standard-library only so it can
  be dropped onto a host without a package install. Test-only dependencies are fine.
- **No new detection weight without evidence.** Adding a component changes every
  published score. If you think a signal is missing, propose it with a fixture that
  demonstrates the gap.
- **Claims must be defensible.** Do not describe heuristic output as a probability,
  a detection rate, or an attribution. Do not add benchmark claims from synthetic
  data.
- **Missing telemetry is never "safe".** Preserve `INSUFFICIENT_EVIDENCE`.

## Development setup

```bash
python -m venv .venv
source .venv/bin/activate
pip install -e '.[dev]'
pytest
```

`make check` runs the same gates as CI: tests, mypy, lint, coverage, and the
documentation checks.

## What to contribute

### A correlation rule (easiest, most useful)

Rules are data, not code — no Python needed. Add a JSON rule and a fixture that
proves it fires on the bad shape and stays quiet on the benign one:

```json
{"id": "my-rule", "title": "…", "severity": "high",
 "steps": [{"event_type": "process_exec", "process_name": "nginx"},
           {"event_type": "file_write", "target": "/etc/*", "within": 20}]}
```

Before proposing it, answer: does it fire on package installs, CGI handlers, or
cron? If yes, tighten `within` or make it two-step. See `docs/rules.md`.

### A fixture

Synthetic JSONL belongs in `datasets/synthetic/` and must be generated by code or
hand-written — never captured from a real host. Start the file with a `#` comment
explaining the shape and that it is synthetic. The schema is in
`docs/event-schema.md`.

### A bug report that is really a detection issue

Include: the fixture, the config (`config_digest`), the command, what you expected,
and what you got. If the score changed between versions, say which.

## Before you open a pull request

1. `pytest` passes and coverage stays at or above 90%.
2. `mypy cabid` is clean.
3. New behaviour has a test; new flags have a CLI test; new report fields appear in
   at least Markdown and JSON.
4. Docs are updated — user-facing behaviour lives in `docs/`, not only in docstrings.
5. `CHANGELOG.md` has an entry under `## [Unreleased]`.
6. No secrets, real hostnames, customer paths, or captured logs in the diff.

Use the pull request template; it asks for exactly these.

## Reporting a security issue

Do **not** open a public issue. See [SECURITY.md](SECURITY.md).

## Style

- Python 3.10+ syntax, `from __future__ import annotations` in new modules.
- Type annotations on public functions; `mypy` must stay clean.
- Prefer plain functions and dicts over classes; this codebase stays readable by
  reading one file at a time.
- Comments explain *why*, especially where a decision is deliberately conservative.
- Every module that produces findings must state in its output what the finding
  does **not** prove.
